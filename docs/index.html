Using only what is known on 31 March 2017, can we predict whether a KKBOX subscriber will churn (not renew within 30 days of plan expiry)? And does their listening behaviour add predictive value beyond their billing records?

table_rowsUnit and target

One row is one subscriber (msno) whose plan comes up for renewal around the end of March 2017. Target: is_churn = 1 if they make no new valid subscription within 30 days after expiry ( of subscribers).

scheduleWhen the prediction is made

On the cutoff date, 31 March 2017. The use case: decide which subscribers to contact. Caveat: the labelled plans expire during March, so for many subscribers the renewal (or its absence) has already happened by the cutoff. We therefore also test a strict 1 March cutoff, before any expiry.

inventory_2What is known then

The member profile, every transaction up to 31 March (plan, price, auto-renew, cancel, expiry date) and daily listening for March 2017. Nothing dated after the cutoff is used, but March transactions overlap the label window (see strict check).

balanceLimits of the claim

Results hold for this KKBOX snapshot only. We show association, not cause: a feature that predicts churn is not proven to cause it. See Limitations.

01Data/ 09

Source, size and key variables

Source: the public Customer Retention Datathon (Riyadh Edition) dataset on Kaggle, released by KKBOX, a music streaming service in Taiwan. Five CSV files (about 2 GB). The label is_churn was defined by KKBOX: a subscriber churns if they make no new valid subscription within 30 days after their membership expires.

Size

  • members rows
  • transactions rows
  • user_logs rows

After joining: labelled subscribers × features, churn. Table-by-table view →

Key variables (33 features in three groups)

Billing • 15

From the full transaction history: auto-renew flag and cancel flag of the last transaction, days until the plan expires, plan length, amount paid, payment method, number of transactions, cancellations, discounts.

Listening • 12

From March 2017 daily logs: active days, hours, songs per day, skip and completion ratios, share of listening in the last 7 days, days since last listen, day-to-day variability.

Demographic • 6

From the member profile: city, registration channel, gender, age, account age, and whether a profile exists.

Class balance

Labelled subscribers by outcome. The imbalance rules out accuracy as the main metric.

Churn by table presence

P profile, T transactions, L March logs. Missing transactions means very high churn.

Strongest single features

ROC-AUC of a feature used alone (training split). Billing dominates.

Quality issues

  • Class imbalance: churners.
  • Age is invalid (0, negative or > 90) for % of member rows; gender blank for %.
  • Not every subscriber is in every table: member profile %, transactions %, March listening logs %.
  • log rows have impossible listening time (< 0 or > 24 h).
  • Money and volume columns are heavily right-skewed.
  • Listening logs cover one month only (March 2017).

Access limits. The data is downloaded from its Kaggle page after accepting the competition rules, so the raw CSVs are not in our repository; the README explains how to get them. Subscriber IDs are anonymised hashes and there are no names or contact details. All plots and summaries: Data Studio.

02Preprocessing/ 09

Choices and why

ChoiceWhy
Aggregate every table to one row per subscriber, using only data up to 31 March 2017 The unit of prediction is the subscriber. Nothing dated after the cutoff is used. However, the labelled plans expire during March, so a March renewal transaction can already be in the features; this is not leakage from the future, but it makes the task easier. A strict check rebuilds billing features from transactions before 1 March (notebook 08).
Left joins, nobody dropped, plus has_member / has_tx / has_logs flags Dropping subscribers missing from any table would remove 25 % of them (65 % if invalid ages also count). Absence is informative: subscribers with no transactions churn at .
No listening logs → zeros and "31 days since last listen" A subscriber with no March plays did listen zero hours; this is the true value, not a missing one.
Ages outside 10–90 → missing; daily listening clipped to [0, 24 h] These values are impossible and would distort means and splits.
Remaining gaps imputed inside each model pipeline (median, fitted on train only); LightGBM uses its native missing-value handling Learning fill values from the training split only keeps validation and test unseen. No feature selection was done: every model uses all 33 features, so no choice depends on held-out data.
log1p + standardisation + one-hot codes, for logistic regression only A linear model needs comparable scales and suffers from heavy skew. Tree models are invariant to monotone transforms, so they get the raw values.
City, registration channel, payment method treated as categories They are ID codes, not quantities.

04Evaluation/ 09

Split and metrics

70 / 10 / 20Split
Stratified random split, seed 42: 70 % train (fit), 10 % validation (model choice, tuning, threshold) and 20 % test (used once). Churn rate is in every part. Split table →
PR-AUCMain metric
Churners are only 9 % of subscribers, so PR-AUC is the main metric; its no-skill level is 0.09. ROC-AUC, log loss and Brier are reported alongside, and log loss is also the tuning objective. Precision, recall, F1 and accuracy are taken at the decision threshold; accuracy is read against the 0.91 of the majority baseline.
τ = Threshold
To flag subscribers we need a cut-off on the probability. We pick the one that maximises F1 on validation, then apply it unchanged to test. F1 weighs a missed churner and a false alarm equally. A business that values a lost subscriber more than a wasted offer should lower τ to raise recall; the cost explorer shows how the best τ moves with that ratio. Any such choice should be made on validation, not test.
1 MarStrict check
Because March transactions overlap the label window, the tuned LightGBM is retrained with billing features from before 1 March 2017 only, on the same split, and scored once on the same test subscribers. Results →
1 000Bootstrap resamples
Test metrics get 95 % intervals from 1 000 bootstrap resamples of the test set; the ablation uses a paired bootstrap (both models scored on the same resample). This shows how much a number could move with another sample of subscribers from the same population. It cannot tell how the model would do in a later month, or why subscribers churn.

07Limitations/ 09

What these results do not show

The 31 March scores are optimistic for early warning

KKBOX defines churn from transactions, and the labelled plans expire during March, so the last March transaction often already shows the renewal decision. The headline PR-AUC means "easy once billing shows the decision", not "we can read intentions". With billing cut at 1 March the model is much weaker (see the strict check).

One snapshot, random split

Train and test subscribers come from the same month. We do not show that the model keeps working for a later month, when prices, promotions or user mix may change.

Hard cases stay hard

Prediction is not causation

Feature importance shows what the model uses, not what makes people leave. For example, switching a subscriber's auto-renew on would not necessarily keep them: auto-renew is partly a sign of an earlier decision to stay. Testing an intervention would need an experiment.

Listening data is thin

Only March 2017 is used, and about a fifth of subscribers have no logs at all. A longer listening history might show a larger effect than our ablation finds.

Threshold and tuning use the same validation split

This makes validation scores slightly optimistic; test scores are not affected because the test split was never used for any choice.

Predictor page is approximate

The predictor runs the real champion model, but asks for 16 inputs; the other features are filled with training medians for similar subscribers. Treat it as an illustration of the model, not a scoring tool. Demographic features (age, city) also raise fairness questions if used for decisions.

Privacy and fairness

Subscriber IDs are anonymised hashes and there are no names or contact details. But age and gender are model inputs, and we did not check whether error rates differ between age or gender groups. Before any real use, audit those groups, and use the scores to offer help to people likely to leave, not to treat them worse.

The Kaggle test set has no labels

The competition test file lists subscribers without the answer. We predict them (results/submission.csv) but cannot score them here, so every number on this page comes from our own labelled test split.

03File overlap/ 09

Who appears in which file

All five files share the subscriber ID msno. The matrix counts distinct subscribers. The diagonal is the size of one file; every other cell is the number of subscribers found in both files, and the small percentage is that overlap as a share of the row file. This is why we left-join everything onto the training and test IDs and add a "has this table" flag instead of dropping subscribers.

04Data quality/ 09

What is missing or wrong, and what we did

Most gaps come from a subscriber being absent from a table. Absence is informative here (for example, subscribers without any transaction churn far more often), so we keep these subscribers and add a flag instead of dropping or blindly filling them.

Issues found

  • Age (bd) is unusable for most members. % of member rows have age 0, negative or above 90. We treat ages outside 10–90 as missing.
  • Gender is mostly blank (% of member rows). We encode it as female / male / not given.
  • No member profile for % of labelled subscribers → has_member = 0; demographics left missing.
  • No transactions for % of subscribers. These churn at → has_tx = 0, counts set to 0, “last transaction” fields left missing.
  • No March listening logs for of subscribers → has_logs = 0, listening totals set to 0, days since last listen = 31.
  • Impossible listening times: daily log rows have total_secs below 0 or above 86 400 (one day); clipped to [0, 86 400].
  • Heavy skew in money and volume columns (skewness of tx_count = ): log1p + scaling for logistic regression only; trees do not need it.

Missing values left after the joins

% of labelled subscribers. Remaining gaps are imputed inside each model pipeline (median, learned on the training split only) or handled natively by LightGBM.

05Churn signals/ 09

Churn signal explorer

Pick a variable to see the churn rate in each group of subscribers. The dashed line is the overall rate. Bar width does not show group size; hover a bar for the count.

Takeaway. Billing state (auto-renew, cancellation, expiry date, plan length) splits subscribers into groups with churn rates near 0 % or near 100 %. Listening behaviour shifts the rate more gently: a silent streak of 15+ days multiplies it about five times, but most listening groups stay close to the average. The models then test whether listening still adds information once billing is known (see Results).
