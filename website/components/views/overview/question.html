Using only what is known on 31 March 2017, can we predict whether a KKBOX subscriber whose plan expires in March 2017 will churn (no new valid subscription within 30 days of that expiry)? And does their listening behaviour add predictive value beyond their billing records?

table_rowsUnit and target

One row is one subscriber (msno) whose plan comes up for renewal around the end of March 2017. Target: is_churn = 1 if they make no new valid subscription within 30 days after expiry ( of subscribers).

scheduleWhen the prediction is made

On the cutoff date, 31 March 2017. The use case: decide which subscribers to contact. Caveat: the labelled plans expire during March, so for many subscribers the renewal (or its absence) has already happened by the cutoff. We therefore also test a strict 1 March cutoff, before any expiry.

inventory_2What is known then

The member profile, every transaction up to 31 March (plan, price, auto-renew, cancel, expiry date) and daily listening for March 2017. Nothing dated after the cutoff is used, but March transactions overlap the label window (see strict check).

balanceLimits of the claim

Results hold for this KKBOX snapshot only. We show association, not cause: a feature that predicts churn is not proven to cause it. See Limitations.

Who did what

Avnish Yadav · 25110067

Data quality, billing, baselines, ablation, errors, Data Studio

My contribution

  • Profiled the five Kaggle tables and found the quality issues: invalid ages, blank gender, impossible listening times and subscribers missing from some tables.
  • Built the 15 billing features from the full transaction history, including the latest-transaction fields.
  • Set up the baselines and tuned logistic regression and the random forest on validation.
  • Ran the feature-group ablation, the error analysis and the failure modes, and designed the Data Studio.

Key choices

  • Left joins with presence flags instead of dropping subscribers: those with no transactions churn at 78.8%, so absence is a signal.
  • log1p and scaling for logistic regression only, because of heavy skew (tx_count skew 22.8); trees get raw values.
  • Logistic regression and random forest settings picked by validation log loss, never by test.

Evaluation

Every learned model beats the auto-renew rule (0.3164) by far: logistic regression 0.8946, random forest 0.9596 test PR-AUC. The ablation shows billing + demographics alone reach 0.9562, and listening adds only +0.0083 [0.0073, 0.0093] at 31 March.

A limitation

The errors concentrate where the data has no warning sign: plans expiring within 30 days, where recall is 0.595. Their billing looks loyal and their listening looks active, so no amount of tuning on these features would fix them.

A small change, and what would happen

If we dropped subscribers missing from any table instead of left-joining, we would lose about 25% of them, including the no-transaction group that churns at 78.8%. The test set would become easier and the scores would look better, but the model would never learn to flag that group, so it would fail on real data.

Ayush Singh · 25110068

Listening and profile features, split, LightGBM, evaluation, leakage, Report

My contribution

  • Built the 12 listening and 6 profile features and joined every table onto the subscriber list with presence flags.
  • Made the stratified 70 / 10 / 20 split and kept every learned preprocessing step on the training split only.
  • Tuned LightGBM with Optuna, set the threshold, ran the test evaluation and the strict 1 March check.
  • Wrote the Report and built the Live Predictor with the tuned LightGBM running in the browser.

Key choices

  • PR-AUC as the main metric: only 9% churn, so always saying "renews" is already 91% accurate.
  • Model chosen by validation log loss, which rewards honest probabilities; threshold τ = 0.45 chosen by F1 on validation; test scored once.
  • No class reweighting, so a predicted 30% still means about 30% churn.

Evaluation

The tuned LightGBM reaches 0.9644 [0.9624, 0.9664] test PR-AUC. A paired bootstrap shows it beats default LightGBM by +0.0025 [0.0016, 0.0038], so the gain is small but real. Validation and test differ by at most about 0.01, so the tuning did not just fit the validation subscribers.

A limitation

0.9644 is an upper bound: by 31 March, March billing often already records the renewal. With billing cut at 1 March the score falls to 0.5682, and even that model still sees listening through March, after many plans have lapsed.

A small change, and what would happen

Lowering τ from 0.45 to 0.20 would catch 16,453 instead of 15,545 test churners (recall 0.913 → 0.966), but false alarms would rise from 2,063 to 3,382 (precision 0.883 → 0.829). That is worth it only if a lost subscriber costs much more than a wasted offer; the threshold and cost explorers in Results show this trade-off for any value.
